  <action>
Extend `include/gps_config.h` with the cadence tunables in the established `#ifndef DEFAULT_GPS_*` shape: `DEFAULT_GPS_MOVING_KMH` 5.0f (upper hysteresis edge — must stay clear of the 2.6 km/h stationary jitter observed on the bench), `DEFAULT_GPS_STATIONARY_KMH` 3.0f (lower hysteresis edge; the gap between the two is what prevents flapping), `DEFAULT_GPS_DEBOUNCE_FIXES` 3 (consecutive confirming accepted fixes required before a state flip), `DEFAULT_GPS_CADENCE_MOVING_S` 8 (emit interval while moving — mid-point of the 5-10 s range GPS-03 specifies), and `DEFAULT_GPS_STATIONARY_HEARTBEAT_S` 0. Document that 0 disables the stationary heartbeat, which is the Phase 1 default because GPS-03 only requires that acceptance pauses when parked; the constant exists so Phase 2's logger can turn on a low-rate "still parked" record without touching cadence logic. Repeat the Assumptions A3/A4/A5 caveat in comments: these are starting points pending a multi-hour stationary test in the real mounting location.

Extend `include/gps_types.h` with `enum class CadenceState : uint8_t { MOVING, STATIONARY }` and `enum class CadenceAction : uint8_t { EMIT, EMIT_HEARTBEAT, SUPPRESS_STATIONARY, SUPPRESS_INTERVAL }`, plus declarations of `const char *cadenceStateName(CadenceState);` and `const char *cadenceActionName(CadenceAction);`.

Create `src/cadence.h` / `src/cadence.cpp` declaring `class Cadence` with `CadenceAction onGatedFix(const Fix &f)`, `CadenceState state() const`, `uint32_t secondsSinceEmit() const` and `bool stateChanged()` (a one-shot flag the caller consumes to know a transition just happened). Initial state is `STATIONARY` — a tracker that has just booted has not proven it is moving, and starting in MOVING would emit a burst of parked points.

`onGatedFix()` runs the state machine first, then the pacing decision:
  - Classify the sample: above `DEFAULT_GPS_MOVING_KMH` is a moving vote, below `DEFAULT_GPS_STATIONARY_KMH` is a stationary vote, and anything inside the band is neither.
  - While in `STATIONARY`, count consecutive moving votes; on reaching `DEFAULT_GPS_DEBOUNCE_FIXES`, switch to `MOVING`, clear both streaks and raise the state-changed flag. While in `MOVING`, do the mirror with stationary votes. Any vote that does not confirm the pending transition — including a sample inside the hysteresis band — resets both streaks to zero, so only an uninterrupted run flips the state.
  - Use `f.speed_kmh` as the movement signal. Do not derive movement from the distance between consecutive positions: stationary position wander on these single-frequency receivers reads as continuous slow motion, whereas the receiver's own Doppler-derived speed does not.
  - Pacing: in `MOVING`, emit when `f.mono_ms` minus the last emit time is at least `DEFAULT_GPS_CADENCE_MOVING_S` seconds, otherwise return `SUPPRESS_INTERVAL`. In `STATIONARY`, return `SUPPRESS_STATIONARY` unless `DEFAULT_GPS_STATIONARY_HEARTBEAT_S` is non-zero and that interval has elapsed, in which case return `EMIT_HEARTBEAT`. Any return value that emits updates the last-emit timestamp from `f.mono_ms`; suppressions do not.
  - All interval arithmetic uses `f.mono_ms` (the monotonic millisecond stamp), never `utc_unix`, which jumps discontinuously when the receiver first acquires the date.
  - Emit immediately on the first accepted fix after entering `MOVING` — a transition into movement should produce a point at once rather than waiting out a full interval.

Wire cadence into `src/main.cpp` at the hand-off point Plan 01 left inside the `GateResult::ACCEPT` branch, and nowhere else. Replace the plain `[ACCEPT]` print with the cadence outcome: `[EMIT]` (or `[EMIT] hb=1` for a heartbeat) carrying the full field set plus `state=`, and `[SUPPRESS] reason=<name> spd=... state=...` otherwise. When `stateChanged()` is set, print a `[STATE]` line naming the old and new state, the speed that triggered it, and the elapsed seconds in the previous state. Extend `[HEALTH]` with the current cadence state, seconds since the last emit, and cumulative emit and suppress counts.

Add a bench simulator to `src/main.cpp`, compiled only when `GPS_BENCH_SIM` is non-zero. Its purpose is to make GPS-02 and GPS-03 provable at a desk in minutes instead of requiring a vehicle and a tunnel. It must feed synthesised snapshots through the identical `FixGate::evaluate()` then cadence path the real fixes take — never a shortcut around either — and every line it produces must carry a `[SIM]` marker so synthetic data can never be mistaken for a real fix in a captured log.

Extend the existing single-character serial command handling (which already owns `r` for raw echo) with:
  - `h` — print a `[HELP]` block listing every command.
  - `+` / `-` — raise or lower the simulated speed by 2 km/h, clamped to 0-150, and report the new value.
  - `s` — toggle the simulator on and off; while on, it synthesises one fix per second from a millisecond timer.
  - `x` — inject one implausible jump: the next synthetic fix is displaced far enough from the previous accepted position that the implied speed exceeds `DEFAULT_GPS_MAX_PLAUSIBLE_KMH`, which must surface as `reason=REJECT_OUTLIER_JUMP`.
  - `z` — inject one fix at coordinates (0,0), which must surface as `reason=REJECT_NULL_ISLAND`.
  - `b` — inject one fix with a deliberately bad quality set (HDOP above `DEFAULT_GPS_HDOP_MAX` and satellite count below `DEFAULT_GPS_SATS_MIN`), which must surface as `reason=REJECT_HDOP`.

The synthetic snapshot is built to be plausible so it legitimately passes the gate on the normal path: `age_ms` 0, `fix_quality` 1, `hdop` 1.0f, `sats` 8, `mono_ms` from `millis()`, `utc_unix` from a fixed base epoch plus elapsed seconds, `course_deg` 90, `alt_m` 10, `speed_kmh` from the current simulated speed, and a position advanced from the previous synthetic position along a due-east bearing by exactly the distance that speed implies over the elapsed time. Anchor the first synthetic position at the last real accepted fix when one exists, otherwise at the known bench coordinates (-22.919952, -43.215005). Advancing the position consistently with the reported speed is what keeps the plausibility check honest: a simulator that held position while claiming 60 km/h would prove nothing, and one that teleported would trip the outlier gate on every sample.

While the simulator is on, ignore real fixes from `poll()` for cadence purposes (still count their bytes and checksums into `[HEALTH]`) so the two sources cannot interleave and produce a nonsensical trajectory.

Write `firmware/gps_tracker/BENCH.md` in the documentation style of `gps_tracker_pinout.md` (Portuguese headings, tables), containing:
