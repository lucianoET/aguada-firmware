# Phase 01.1: Code Review Report

**Reviewed:** 2026-08-03T10:37:56Z
**Depth:** standard
**Files Reviewed:** 18 (main.cpp + 4 driver modules + i2c_bus + cadence + gps_reader + config/build/docs)
**Status:** issues_found

## Summary

Reviewed the Fase 01.1 I2C peripheral additions (i2c_bus, accel_sensor, mag_sensor,
env_sensor, display) and their wiring into main.cpp, alongside the unchanged-in-spirit
cadence/gps_reader modules and the phase's docs (BENCH.md, gps_tracker_pinout.md,
gps_config.h, platformio.ini).

The individual driver modules are well-structured and mostly honor their own stated
contracts (non-blocking, last-known-value fallback, i2c_bus-mediated error reporting).
However, the integration glue in `main.cpp::i2cRecoverTick()` has a real correctness bug
that silently defeats the whole online/offline health model the phase's design (D-12/D-13)
depends on: it forces every recovered module to report `online` regardless of whether the
driver's own re-initialization actually succeeded. Combined with a second bug where
`i2c_bus::present()` never reflects anything beyond the one-time boot scan, DISPLAY/MAG
modules that were not wired at boot can never be recovered at runtime even though the
retry-probe logic thinks they can. There is also a real (if currently probably benign on
the GCC/Xtensa toolchain in use) unspecified-evaluation-order bug in the raw accelerometer
byte assembly. See details below.

## Critical Issues

### CR-01: `i2cRecoverTick()` forces modules "online" regardless of the driver's own re-init result

**File:** `firmware/gps_tracker/src/main.cpp:503-532`
**Issue:**
`i2c_bus.h`'s documented contract is explicit: *"Driver reports its own begin() result...
Passing true clears the consecutive-error counter"* (`i2c_bus.h:68-71`), and each driver's
own `begin()` correctly calls `i2c_bus::setOnline(module, ok)` with the real result
(see `accel_sensor.cpp:52`, `mag_sensor.cpp:108/123`, `env_sensor.cpp:33`,
`display.cpp:69/80/86`).

But `i2cRecoverTick()` in `main.cpp` discards that result and unconditionally forces the
module back online right after calling `begin()`:

```cpp
case I2cModule::ACCEL:
    accel_sensor::begin();          // return value discarded
    i2c_bus::setOnline(m, true);    // forced online no matter what begin() reported
    break;
```

(same pattern for `DISPLAY`, `MAG`, `ENV` at lines 507-509, 511-515, 517-522, 524-528).

This is the *only* reinit path actually exercised at runtime (see WR-01 below), so it is
not a hypothetical: whenever `i2c_bus::tick()`'s live probe (`i2c_bus.cpp:93-115`,
`probeAddr()`) gets a bare I2C ACK from an address but the driver's own more specific
handshake then fails — WHO_AM_I mismatch for the accelerometer, a wrong/absent chip for the
compass (`s_chip == MagChip::NONE`), a failed `Adafruit_HTU21DF::begin()`, or a failed
`U8g2::begin()` — the module gets marked `online` anyway. `[HEALTH]` will then report e.g.
`mag=on mag_chip=none`, `accel=on` while `accel_g=` is reading garbage, or `disp=on` while
the OLED was never actually configured — directly contradicting the field-diagnosis
guidance documented in `BENCH.md:179-188` ("`off` persistente ... indica falha de fiação ou
endereço errado") and defeating D-12/D-13's core promise.

**Fix:** capture and honor the driver's own return value instead of forcing `true`:
```cpp
case I2cModule::ACCEL: {
    bool ok = accel_sensor::begin();
    if (!ok) { i2c_bus::clearReinit(m); continue; }  // begin() already reported offline
    break;
}
```
(apply the same pattern to DISPLAY/MAG/ENV; only print `"[I2C] %s recovered"` and proceed
to `clearReinit()` when `begin()` actually returned `true`).

### CR-02: `i2c_bus::present()` never reflects anything beyond the one-time boot scan — DISPLAY/MAG can never recover if absent at boot

**File:** `firmware/gps_tracker/src/i2c_bus.cpp:121-137`, `firmware/gps_tracker/src/i2c_bus.cpp:195`,
consumed by `firmware/gps_tracker/src/display.cpp:62-66` and `firmware/gps_tracker/src/mag_sensor.cpp:82-89`
**Issue:**
`s_present[128]` is populated exactly once, during `i2c_bus::begin()`'s boot-time scan
(`i2c_bus.cpp:130-137`). Nothing ever updates it afterward — `retryProbe()`
(`i2c_bus.cpp:93-115`), which is the function that actually drives runtime recovery via a
*live* `Wire.beginTransmission/endTransmission` probe, only updates `s_boundAddr[]`, never
`s_present[]`.

`display::begin()` and `mag_sensor::begin()` both gate their address selection on
`i2c_bus::present(ADDR)` (`display.cpp:62-66`, `mag_sensor.cpp:83-89`) — i.e. the *stale,
boot-time-only* cache — rather than trusting `retryProbe()`'s live result that just proved
the address answers now. Consequently: if the OLED or the compass was **not** physically
wired at boot time, `i2c_bus::present()` permanently returns `false` for their addresses,
so `display::begin()`/`mag_sensor::begin()` can never succeed again for the lifetime of the
boot — even after `i2c_bus::tick()`'s `retryProbe()` has confirmed the address is live and
scheduled a reinit. This silently and permanently breaks the D-13 "recuperação em runtime"
promise for exactly the two modules whose docs claim it (`i2c_bus.h:88-90`), for the
"connect it after boot" case. (ACCEL and ENV are unaffected — their `begin()` implementations
do their own live Wire probe / library `begin()` call and never consult `i2c_bus::present()`.)

Note the BENCH.md D-13 test procedure (`BENCH.md:251-256`) only exercises
*disconnect-then-reconnect of an already-present-at-boot* module, so this gap would not be
caught by that specific roteiro, but it directly contradicts D-12's "cada subconjunto
funciona de forma independente" claim once a technician wires up the display or compass
after the tracker has already booted.

**Fix:** either have `retryProbe()` set `s_present[addr] = true` on a successful live probe,
or change `display::begin()`/`mag_sensor::begin()` to perform their own live
`Wire.beginTransmission`/`endTransmission` probe instead of trusting the boot-time-only
`i2c_bus::present()` cache.

## Warnings

### WR-01: Unspecified evaluation order in raw 16-bit accelerometer byte assembly

**File:** `firmware/gps_tracker/src/accel_sensor.cpp:87-89`
**Issue:**
```cpp
int16_t axRaw = (static_cast<int16_t>(Wire.read()) << 8) | Wire.read();
int16_t ayRaw = (static_cast<int16_t>(Wire.read()) << 8) | Wire.read();
int16_t azRaw = (static_cast<int16_t>(Wire.read()) << 8) | Wire.read();
```
Each line calls `Wire.read()` twice with side effects (each call consumes the next byte
from the internal I2C receive buffer, so it matters which one runs first). The C++ standard
does not specify an evaluation order between the two operands of the built-in `|` operator
(the left-to-right sequencing C++17 added only applies to `<<`/`>>` themselves, not to `|`
combining their result with another call). A compiler/optimization level that evaluates the
right-hand `Wire.read()` before the left-hand one would silently swap the high and low
bytes of every axis, corrupting `magnitude_g` and therefore the wake-debounce logic
(D-05/D-06) and Cadence's accelerometer promotion path — with no error reported anywhere
(this is unspecified, not a crash).
**Fix:** force the read order with separate statements:
```cpp
uint8_t axHi = Wire.read(), axLo = Wire.read();
uint8_t ayHi = Wire.read(), ayLo = Wire.read();
uint8_t azHi = Wire.read(), azLo = Wire.read();
int16_t axRaw = (static_cast<int16_t>(axHi) << 8) | axLo;
int16_t ayRaw = (static_cast<int16_t>(ayHi) << 8) | ayLo;
int16_t azRaw = (static_cast<int16_t>(azHi) << 8) | azLo;
```
(NB: `uint8_t axHi = Wire.read(), axLo = Wire.read();` still has the same ordering problem
within one declaration — use two separate statements per axis, not a comma-separated
declaration, to guarantee the sequence point between the two reads.)

### WR-02: Per-driver `reinitDue()` handling in `poll()`/`render()` is dead code, duplicating (and diverging from) `main.cpp`'s actual recovery path

**File:** `firmware/gps_tracker/src/accel_sensor.cpp:60-66`, `firmware/gps_tracker/src/mag_sensor.cpp:133-139`,
`firmware/gps_tracker/src/env_sensor.cpp:41-47`, `firmware/gps_tracker/src/display.cpp:95-101`,
vs. `firmware/gps_tracker/src/main.cpp:496-537`
**Issue:** Every driver documents and implements its own "if offline, check
`i2c_bus::reinitDue()` and re-attempt `begin()`" branch, e.g.:
```cpp
bool accel_sensor::poll() {
    if (!i2c_bus::online(I2cModule::ACCEL)) {
        if (i2c_bus::reinitDue(I2cModule::ACCEL)) {
            begin();
            i2c_bus::clearReinit(I2cModule::ACCEL);
        }
        return false;
    }
    ...
```
But `main.cpp::loop()` calls each driver's scheduled `poll()`/`render()` *before* calling
`i2cRecoverTick()` (which is what actually calls `i2c_bus::tick()` and thus is the only
place that ever sets `reinitPending`). `i2cRecoverTick()` then immediately consumes and
clears that same flag within the same `loop()` iteration it was set
(`main.cpp:499-536`), before any driver's own next scheduled `poll()`/`render()` call (which
only happens on a later iteration) can ever observe `reinitDue() == true`. In practice, the
branches quoted above never execute — `i2cRecoverTick()` is the sole reinit path exercised,
and (per CR-01) it has a bug the driver-local code above does not have. This is a
maintainability hazard: two implementations of the same responsibility exist, only one of
which runs, and the header-level documentation for each driver's `poll()`
(e.g. `accel_sensor.h:33-39`) describes behavior that is not actually reachable.
**Fix:** remove the dead per-driver branches (rely solely on `i2cRecoverTick()`) or,
if defense-in-depth is desired, reorder `main.cpp::loop()` so `i2c_bus::tick()` runs
*before* the per-driver polls each iteration, and drop `i2cRecoverTick()`'s own
begin()-calling logic in favor of the per-driver one (fixing CR-01 in the process).

## Info

### IN-01: `[HEALTH]`'s `hdg_src=` uses `everAccepted` instead of the same freshness gate the OLED uses

**File:** `firmware/gps_tracker/src/main.cpp:682-684` vs. `firmware/gps_tracker/src/main.cpp:396,407-409`
**Issue:** `buildDisplayState()` arbitrates heading using `haveFreshFix` (fix accepted *and*
still within `DEFAULT_GPS_FRESH_MS`), correctly falling back once a fix goes stale. The
`[HEALTH]` line recomputes the same arbitration with `everAccepted` (true forever after the
first accepted fix, regardless of staleness), so after GPS lock is lost mid-session the
OLED and `[HEALTH]`'s `hdg_src=` field can disagree about whether the heading source is
`mag` or `gps`, which is exactly the D-08 field the BENCH.md roteiro (`BENCH.md:226-230`)
tells an operator to trust for calibration/diagnosis.
**Fix:** compute `haveFreshFix` once per loop iteration (or expose it from
`buildDisplayState()`) and reuse it for the `[HEALTH]` `arbitratedHeading()` call instead of
`everAccepted`.

### IN-02: Pinout doc omits the third auto-detected compass chip/address

**File:** `firmware/gps_tracker/gps_tracker_pinout.md:29-34`
**Issue:** The Fase 01.1 module/address table lists only HMC5883L (0x1E) and QMC5883L
(0x0D, "muitos GY-271 vêm com QMC5883L"), but `gps_config.h:136-138`
(`DEFAULT_MAG_ADDR_VCM 0x0C`) and `mag_sensor.cpp:87-89,116-118` explicitly detect and
support a third chip, VCM5883L, as documented in `BENCH.md:185` (`mag_chip=`
"HMC5883L`/`QMC5883L`/`VCM5883L`/`none`"). The pinout table is out of sync with the
implemented/documented candidate list.
**Fix:** add a VCM5883L (0x0C) row to the table in `gps_tracker_pinout.md`.

### IN-03: `i2c_bus::foundCount()` is unused

**File:** `firmware/gps_tracker/src/i2c_bus.h:55`, `firmware/gps_tracker/src/i2c_bus.cpp:197`
**Issue:** `foundCount()` is part of the public contract and implemented, but nothing in
`main.cpp` (setup banner or `[HEALTH]`) ever calls it — dead public API.
**Fix:** either surface it (e.g. in the setup banner alongside the per-module
disp/accel/mag/env summary already printed at `i2c_bus.cpp:168-172`) or remove it if it's
not needed by a later phase.
