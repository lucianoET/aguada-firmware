## User Constraints (from CONTEXT.md)

### Locked Decisions

**Display (SSD1306)**
- D-01: Single dense screen — fix/sats/HDOP, speed, heading, temp/humidity, cadence state (MOVING/STOPPED), all visible at once. No pagination, no buttons.
- D-02: Refresh at 1 Hz, aligned to the GPS fix.
- D-03: No fix (cold start): live acquisition screen — "NO FIX" + sats in view + uptime + readings from sensors that are ALREADY alive (temp/hum, heading, movement). Confirms wiring while waiting for fix.
- D-04: Speed unit selectable via build flag (`DEFAULT_SPEED_UNIT`), km/h default, knots (kt) for boat. Heading in degrees + cardinal.

**MPU6050 → cadence**
- D-05: Hybrid role: accel detects stopped→moving instantly (GPS takes several fixes to see speed); GPS speed remains the authority for moving→stopped. Fast resume without logging drift points.
- D-06: Detection by polling the accel over I2C (magnitude + software threshold/debounce). No INT wire this phase.
- D-07: Accel only — gyroscope not used this phase.

**Heading (HMC5883)**
- D-08: Heading source blended by speed: compass when stopped/slow (GPS course is garbage below ~3 km/h), GPS course when moving.
- D-09: Hard-iron calibration via serial command ("cal" on USB serial → rotate the module → min/max offsets persisted in NVS). Re-calibratable after installation without recompiling.
- D-10: Flat mounting assumed in v1 — no tilt compensation. Magnetic declination via build flag `DEFAULT_MAG_DECLINATION` (0 default).
- D-11: Many GY-271 boards ship QMC5883L (0x0D) instead of HMC5883L (0x1E) — firmware must detect and support both.

**Sensor roles & failure policy**
- D-12: Total graceful degradation: I2C scan at boot; missing module → feature disabled, indicated on display/serial, rest keeps running. GPS tracking never blocked by a peripheral failure. Any subset of the 4 modules works.
- D-13: Runtime failure (loose wire, bus error): mark offline after N consecutive errors, re-init retry every ~10s, comes back on its own when reconnected.
- D-14: HTU21: display + serial only this phase. Log/MQTT integration comes in Phases 2/3.

## Summary

This phase adds four separate I2C breakout modules — SSD1306 OLED (0x3C), MPU6050 (0x68), HMC5883L/QMC5883L (0x1E/0x0D), HTU21D (0x40) — onto the same GPIO6/GPIO7 `Wire` bus already used by the AirQ node elsewhere in this repo, and wires their output into the existing `gps_reader → fix_gate → cadence` pipeline and a new OLED status screen. The core engineering risk is not any single library choice, it is **time-budget discipline in a single-threaded superloop**: `gps_reader.poll()` drains a 256-byte UART ring buffer every `loop()` iteration, and any I2C peripheral work (display transfer, sensor conversion wait) that blocks for too long, too often, starves that buffer and manifests as dropped NMEA sentences / `REJECT_STALE`. The existing `firmware/node/src/ani_sensor.cpp` pattern in this repo uses a `delay(10)` polling loop with up to a 1-second deadline waiting for sensor data — that exact pattern must **not** be ported here; the AirQ node has no time-critical UART consumer competing for the CPU, the GPS tracker does.

Library choices favor small, single-purpose drivers over full-featured suites: **U8g2** (not Adafruit SSD1306+GFX) for the display, because D-01's dense single-screen layout needs U8g2's wide selection of compact bitmap fonts to fit fix/sats/HDOP/speed/heading/temp/humidity/cadence on one 128×64 frame; **DFRobot_QMC5883** for the compass, because it is the only readily available library confirmed (via direct source inspection) to auto-detect both the HMC5883L (0x1E) and QMC5883L (0x0D) chip variants — a direct, exact match for D-11; **a hand-rolled raw-I2C driver** (no library) for the MPU6050, because D-07 scopes this phase to accel-only magnitude thresholding, and pulling in a full DMP/I2Cdev-based library (ElectronicCats/MPU6050 or i2cdevlib) for a 6-register read is disproportionate flash/RAM cost for what this phase needs — consistent with this milestone's own established pattern of hand-rolling small protocols (raw UBX GPS config bytes) rather than reaching for heavyweight libraries; and **Adafruit HTU21DF Library** for temp/humidity, matching the Adafruit ecosystem this repo's node firmware already depends on (`Adafruit_BusIO`).

**Primary recommendation:** Use U8g2 (full-buffer, hardware I2C) for the display, DFRobot_QMC5883 for the compass (dual-chip auto-detect), a hand-rolled raw-I2C reader for MPU6050 accel-only, and Adafruit HTU21DF for temp/humidity — all sharing one `Wire` bus at a single clock speed (400 kHz recommended, with 100 kHz as the documented fallback if the 4-module parallel pull-up bus proves unreliable on the bench) — and schedule every sensor poll and the display render on independent `millis()`-based timers in `loop()`, never stacking more than one blocking I2C operation per `loop()` pass, exactly mirroring the existing `lastHealthMs`/`DEFAULT_GPS_HEALTH_PERIOD_MS` non-blocking-timer pattern already in `main.cpp`.

## Architectural Responsibility Map

This is embedded firmware, not a web app — the table below adapts the browser/API/DB tiers to this project's actual layers: **Driver** (raw I2C register access), **Application/State** (cadence, heading arbitration, wake detection, bus health), **Presentation** (OLED + USB serial), **Persistence** (NVS/Preferences).

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| SSD1306 pixel/font rendering | Driver (U8g2) | Presentation | U8g2 owns the SSD1306 init sequence and font rendering; `main.cpp` only decides *what* to draw |
| Dense status screen composition (D-01) | Presentation (`main.cpp` / new display module) | Application/State | Layout and which fields to show is a presentation concern fed by state already computed elsewhere |
| Accel magnitude + wake threshold (D-05/D-06) | Application/State | Driver | The threshold/debounce decision belongs with cadence-adjacent logic; the driver only returns raw g-values |
| MPU6050 register read | Driver (hand-rolled raw I2C) | — | No state, no decisions — pure register I/O |
| Heading arbitration (compass vs GPS course, D-08) | Application/State | — | Speed-based source selection is a business-logic decision, not a driver concern |
| HMC5883L/QMC5883L raw field read + chip detection | Driver (DFRobot_QMC5883) | — | Register-map differences are exactly what the library abstracts away |
| Hard-iron calibration min/max capture (D-09) | Application/State | Persistence | Capture logic lives with the serial command handler; only the resulting offsets are persisted |
| Calibration offset storage | Persistence (Preferences/NVS) | — | Must survive reboot/recompile per D-09 |
| I2C bus health / boot scan / per-module retry (D-12/D-13) | Application/State (bus manager) | Driver | Cross-cuts all 4 drivers; owned once, not duplicated per sensor |
| GPS UART parsing, fix gating, cadence pacing (existing) | Application/State (`gps_reader`/`fix_gate`/`cadence`) | — | Unchanged this phase; peripherals must never be able to block this path |

### Pattern 1: Non-blocking per-peripheral scheduling (extends existing `[HEALTH]` timer pattern)

**What:** Each peripheral gets its own `static uint32_t lastPollMs` and `if (millis() - lastPollMs >= DEFAULT_X_POLL_MS)` guard in `loop()`, exactly like the existing `lastHealthMs`/`DEFAULT_GPS_HEALTH_PERIOD_MS` pattern already in `main.cpp`.
**When to use:** For every I2C peripheral poll and the display render — never poll/render unconditionally on every `loop()` iteration.
**Example:**
```cpp
// Source: pattern generalized from firmware/gps_tracker/src/main.cpp's existing
// `if (millis() - lastHealthMs >= DEFAULT_GPS_HEALTH_PERIOD_MS)` block.
static uint32_t lastAccelPollMs = 0;
static uint32_t lastMagPollMs   = 0;
static uint32_t lastEnvPollMs   = 0;
static uint32_t lastDisplayMs   = 0;

void loop() {
    // ... existing gps_reader.poll() / fixGate / cadence pass runs first, unchanged ...

    if (millis() - lastAccelPollMs >= DEFAULT_ACCEL_POLL_MS) {
        lastAccelPollMs = millis();
        accelSensor.poll();   // single 6-byte I2C burst read, sub-millisecond at 400kHz
    }
    if (millis() - lastMagPollMs >= DEFAULT_MAG_POLL_MS) {
        lastMagPollMs = millis();
        magSensor.poll();
    }
    if (millis() - lastEnvPollMs >= DEFAULT_HTU21_POLL_MS) {
        lastEnvPollMs = millis();
        envSensor.poll();     // internally blocks ~50ms (Adafruit lib's delay(50)) —
                               // this is why it is scheduled every few seconds, never every loop
    }
    if (millis() - lastDisplayMs >= DEFAULT_DISPLAY_REFRESH_MS) {
        lastDisplayMs = millis();
        display.render(lastFix, lastResult, cadence.state(), accelSensor, magSensor, envSensor);
    }
}
```

### Pattern 2: Boot-time I2C scan with per-module online flags (D-12)

**What:** A single full-bus scan (addresses 0x08-0x77) at boot, logged once, used to set 4 independent `bool` online flags — never gate the rest of the firmware on "all 4 present."
**When to use:** Startup, before attempting any sensor `.begin()` call.
**Example:**
```cpp
// Source: adapted from the existing repo pattern in
// firmware/node/src/ani_sensor.cpp's ani_init() I2C scan loop.
Wire.begin(DEFAULT_I2C_SDA_PIN, DEFAULT_I2C_SCL_PIN);
Wire.setClock(DEFAULT_I2C_CLOCK_HZ);
for (uint8_t addr = 0x08; addr <= 0x77; addr++) {
    Wire.beginTransmission(addr);
    if (Wire.endTransmission() == 0) {
        Serial.printf("[I2C] found 0x%02X\n", addr);
    }
}
// Each module's own begin() then independently succeeds/fails; a missing
// module never prevents the others (or the GPS pipeline) from working.
```

### Pattern 3: Speed-blended heading arbiter reusing the existing cadence threshold (D-08)

**What:** Below `DEFAULT_GPS_STATIONARY_KMH` (already defined in `gps_config.h` for cadence's hysteresis band), use the compass heading; at/above it, use GPS course.
**When to use:** Any time the display needs a heading value to render.
**Example:**
```cpp
// Source: reuses firmware/gps_tracker/include/gps_config.h's existing
// DEFAULT_GPS_STATIONARY_KMH (3.0f) — the same value the user's D-08
// decision independently specified ("~3 km/h") for exactly this purpose.
// This is a genuine single-source-of-truth opportunity: do not introduce a
// second DEFAULT_MAG_HEADING_SPEED_KMH constant that could drift from
// DEFAULT_GPS_STATIONARY_KMH over time.
float displayHeadingDeg(const Fix &f, float compassHeadingDeg) {
    return (f.speed_kmh < DEFAULT_GPS_STATIONARY_KMH) ? compassHeadingDeg : f.course_deg;
}
```

### Pattern 4: Raw MPU6050 accel-only read (hand-rolled, no library)

**What:** WHO_AM_I check, wake, single burst read, magnitude compare.
**When to use:** D-06/D-07's accel-only wake detection.
**Example:**
```cpp
// Source: register addresses cross-checked against InvenSense MPU-6050
// register map via lastminuteengineers.com and controllerstech.com
// tutorials [CITED]. Sensitivity 16384 LSB/g is the MPU6050's default
// ±2g full-scale range (register 0x1C left at power-on-reset value).
bool mpu6050Init(uint8_t addr) {
    Wire.beginTransmission(addr);
    Wire.write(0x75);                 // WHO_AM_I
    if (Wire.endTransmission(false) != 0) return false;
    Wire.requestFrom(addr, (uint8_t)1);
    if (!Wire.available() || Wire.read() != 0x68) return false;

    Wire.beginTransmission(addr);
    Wire.write(0x6B); Wire.write(0x00);   // PWR_MGMT_1 = 0 → wake from sleep
    return Wire.endTransmission() == 0;
}

float mpu6050AccelMagnitudeG(uint8_t addr) {
    Wire.beginTransmission(addr);
    Wire.write(0x3B);                 // ACCEL_XOUT_H
    Wire.endTransmission(false);
    Wire.requestFrom(addr, (uint8_t)6);
    int16_t ax = (Wire.read() << 8) | Wire.read();
    int16_t ay = (Wire.read() << 8) | Wire.read();
    int16_t az = (Wire.read() << 8) | Wire.read();
    float gx = ax / 16384.0f, gy = ay / 16384.0f, gz = az / 16384.0f;
    return sqrtf(gx*gx + gy*gy + gz*gz);
}
```

### Pattern 5: Calibration offsets via Preferences (D-09)

**What:** A dedicated namespace, written only from the "cal" serial command handler, read once at boot.
**When to use:** Hard-iron min/max offset persistence.
**Example:**
```cpp
// Source: Arduino-ESP32 Preferences API [CITED: docs.espressif.com/projects/
// arduino-esp32 Preferences]. Use a namespace distinct from any other module's
// (e.g. "magcal") — Preferences only holds one namespace open at a time per
// object instance.
#include <Preferences.h>
Preferences magPrefs;

void saveMagCalibration(float xMin, float xMax, float yMin, float yMax) {
    magPrefs.begin("magcal", false);
    magPrefs.putFloat("xMin", xMin);
    magPrefs.putFloat("xMax", xMax);
    magPrefs.putFloat("yMin", yMin);
    magPrefs.putFloat("yMax", yMax);
    magPrefs.end();
}

void loadMagCalibration(float &xMin, float &xMax, float &yMin, float &yMax) {
    magPrefs.begin("magcal", true);   // read-only
    xMin = magPrefs.getFloat("xMin", 0.0f);
    xMax = magPrefs.getFloat("xMax", 0.0f);
    yMin = magPrefs.getFloat("yMin", 0.0f);
    yMax = magPrefs.getFloat("yMax", 0.0f);
    magPrefs.end();
}
```

### Anti-Patterns to Avoid

- **Porting `ani_sensor.cpp`'s `while (!available) delay(10)` wait loop verbatim:** That pattern blocks for up to 1000ms with nothing competing for the CPU on the AirQ node. On the GPS tracker, a 1000ms block can overflow the 256-byte/~266ms GPS UART ring buffer several times over, silently dropping NMEA sentences. Any "wait for sensor ready" loop on this firmware needs an upper bound far below that, or must not block at all (poll a "ready" flag across `loop()` iterations instead of spinning inside one call).
- **Setting `Wire.setClock()` per-sensor:** Arduino's `Wire`/`TwoWire` is a single global bus instance — the last `setClock()` call wins for every device until changed again. Pick one clock speed for the whole 4-module bus (400kHz recommended; the pinout doc's own note that the parallel pull-ups sit around ~1-2kΩ supports 400kHz, but documents 100kHz as the fallback if the bench bus proves unreliable with all 4 modules attached).
- **Introducing a second heading-threshold constant instead of reusing `DEFAULT_GPS_STATIONARY_KMH`:** see Pattern 3 — this is a real single-source-of-truth trap, not a hypothetical one, since the user's own D-08 wording ("~3 km/h") already matches the existing constant's value.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SSD1306 low-level init/contrast/addressing sequences | A raw I2C SSD1306 command sequence from the datasheet | U8g2 | Dozens of clone-panel quirks (different reset sequences, contrast defaults) are already handled; hand-rolling reintroduces bugs this library fixed years ago |
| HMC5883L vs QMC5883L register-map differences and heading math | A custom dual-branch driver reading raw registers for each chip | `DFRobot_QMC5883` | The two chips have different addresses, register maps, *and* output scaling — the library already normalizes this into one `getHeadingDegrees()` call, exactly D-11's requirement |
| NVS/flash-backed key-value calibration storage | Raw flash-partition read/write for the mag offsets | `Preferences` (built-in) | Wear-leveling, crash-safety, and the key/value API are already solved at the ESP-IDF NVS layer — hand-rolling flash writes for 4 floats is pure risk for zero benefit |
| HTU21D's CRC-checked I2C read protocol and 12/14-bit resolution config | A custom I2C sequence per the HTU21D datasheet | `Adafruit HTU21DF Library` | Small, single-purpose, already handles the sensor's specific command/response timing |

**Key insight:** The one place this phase *should* hand-roll (MPU6050 raw accel read) is a deliberate exception, not a contradiction of the rule above — it is justified because the phase's actual requirement (D-07: accel magnitude only, no gyro, no DMP) is genuinely smaller than what any available library provides, and pulling in a full-featured library would add flash/RAM cost with no corresponding feature use. Don't generalize this exception to the OLED, compass, or humidity sensors — those all involve real protocol/format complexity (font rendering, dual-chip register maps, CRC framing) that a library correctly owns.

## Common Pitfalls

### Pitfall 1: Blocking I2C reads starve the GPS UART buffer

**What goes wrong:** `gps_reader.poll()` drains a ~256-byte software ring buffer every `loop()` call (Arduino-ESP32 default `HardwareSerial` RX buffer size). At 9600 baud that buffer fills in ~266ms. Any I2C peripheral call that blocks for a comparable or larger duration — repeated often enough, or stacked with others in the same `loop()` pass — causes dropped NMEA bytes, manifesting as `REJECT_STALE`/`REJECT_NO_FIX` in the existing gate-counter `[HEALTH]` log.
**Why it happens:** This repo already has a working reference implementation of exactly the anti-pattern to avoid: `firmware/node/src/ani_sensor.cpp`'s `ani_read()` contains `while (!s_ens.available() && millis() < deadline) { delay(10); }` with a 1000ms deadline, and `Adafruit_HTU21DF`'s own `readTemperature()`/`readHumidity()` internally call `delay(50)` while waiting for conversion. Copying the AirQ pattern's philosophy ("just wait until the sensor answers") onto a firmware with a time-critical UART consumer is the natural but wrong instinct.
**How to avoid:** Schedule each peripheral independently via `millis()`-based timers (Pattern 1) so at most one "slow" (10-50ms) blocking call happens per `loop()` iteration, and space the slowest one (HTU21D, ~50ms per read) several seconds apart (`DEFAULT_HTU21_POLL_MS` ≈ 3000-5000ms is a comfortable margin against the ~266ms buffer budget). Never adopt a `while(...) delay(10)` spin with a deadline anywhere near or above ~100-150ms on this firmware.
**Warning signs:** `[HEALTH]` line's `no_fix=`/`stale=` counters climbing after peripherals are wired in, when they were flat during Phase 1 bench testing; NMEA checksum failures (`gpsReader.failedChecksum()`) increasing.

### Pitfall 2: `Wire` is a single global bus — one clock speed for 4 different chips

**What goes wrong:** Calling `Wire.setClock()` inside one sensor's driver (e.g. if a pulled-in library sets its own preferred speed on `begin()`) silently changes the speed for every other device on the bus until something else changes it back — this exact defensive re-set pattern already exists in `ani_sensor.cpp` (`Wire.begin(sda_pin, scl_pin); Wire.setClock(50000);` called again *after* each library's own `begin()`, specifically to undo a speed change a library init made).
**Why it happens:** Arduino's I2C abstraction models one `TwoWire` object per bus, not per device — libraries that call `Wire.setClock()` internally (common in display/sensor libraries as a defensive "make sure it's fast enough" measure) can override whatever the application chose.
**How to avoid:** Set `Wire.setClock(DEFAULT_I2C_CLOCK_HZ)` once after every `.begin()` call that might have touched it (mirroring `ani_sensor.cpp`'s existing restore-after-init pattern), and pick one speed (400kHz recommended) that all 4 datasheets support rather than the AirQ node's conservative 50kHz choice — the pinout doc's own note about the combined ~1-2kΩ parallel pull-up already anticipates 400kHz operation, with 100kHz documented as the explicit fallback if the bench bus misbehaves with all 4 modules attached.
**Warning signs:** One sensor's readings become intermittently garbled/NACKed only after a *different* sensor's driver is added to the build — a signature of an unexpected clock-speed change.

### Pitfall 3: I2C bus hang / clock-stretch stall with no timeout

**What goes wrong:** The Arduino-ESP32 `Wire`/`TwoWire` implementation has historically shipped with I2C transaction code that can loop without a timeout if a device holds SCL low (clock stretching) or the bus otherwise locks up — a documented, long-standing issue (`espressif/arduino-esp32#349`), though recent cores default to a 50ms bus timeout. A single glitchy module (loose wire, brief brownout) can therefore hang the entire `loop()`, which — per Pitfall 1 — directly threatens the GPS pipeline.
**Why it happens:** I2C is an open-drain, multi-master-capable bus by design; a slave device malfunctioning mid-transaction (or a floating SDA/SCL from a loose bench wire, explicitly a real risk here per D-13's own framing) can leave the line stuck low with no protocol-level guarantee the master's driver recovers gracefully.
**How to avoid:** Implement D-13's own requirement properly: track consecutive I2C errors (`Wire.endTransmission()` return code != 0, or `Wire.requestFrom()` returning fewer bytes than requested) per module, mark that module offline after N consecutive failures (a small N like 3-5 is a reasonable starting point `[ASSUMED]`), and retry re-init on a ~10s timer rather than every loop. If a full bus lock-up is observed on the bench (not just one bad device), the documented I2C-spec recovery is toggling SCL manually for up to 9 clock pulses to un-stick a slave holding SDA low — worth keeping as a documented fallback, not necessarily implementing preemptively unless bench testing shows it's needed.
**Warning signs:** The whole firmware appears to freeze (LED stops blinking, no new `[HEALTH]` lines) rather than just one sensor's readings going stale — that asymmetry (one bad wire freezing everything vs. only that sensor's feature disabling) is the signal that timeout/recovery is missing or insufficient.

### Pitfall 4: Cadence's documented single-call-site contract needs a deliberate, visible extension for D-05

**What goes wrong:** `cadence.h`'s own header comment states: *"the only call site is main.cpp's single GateResult::ACCEPT branch, never anywhere else, so an ungated fix can never reach this state machine and flip moving/stationary."* D-05 requires an accel-derived signal to flip STATIONARY→MOVING *outside* that GPS-fix-gated path. If this is implemented by quietly adding a second call path without updating the class's own documented invariant, a future contributor (or this project's own future phases) reading that comment will believe an invariant holds that no longer does.
**Why it happens:** The path of least resistance is to add an `if (accelWake) cadence.forceState(MOVING)`-style shortcut directly in `main.cpp` without touching `cadence.h`/`cadence.cpp`'s contract or its documentation, because the existing code is well-factored and "just calling a new method" feels non-invasive.
**How to avoid:** Treat this as a deliberate, documented contract change: add an explicit new entry point (e.g. `Cadence::onAccelWake()`) alongside `onGatedFix()`, update the class-level comment to state both call sites and their asymmetric authority (accel can only promote STATIONARY→MOVING; only a GPS-gated fix via `onGatedFix()` can demote MOVING→STATIONARY, per D-05), and keep the demotion path exactly as today (`onGatedFix()`'s hysteresis/debounce unchanged). This keeps the state machine's logic auditable rather than accreting undocumented side-entry points.
**Warning signs:** Code review or a future phase finds two different places that can flip `cadence.state()`, with only one of them mentioned in the class's own documentation.

### Pitfall 5: New "cal" serial command collides with the existing single-character bench-sim hotkey dispatch

**What goes wrong:** `main.cpp`'s `loop()` currently reads one character at a time from `Serial` and dispatches immediately (`r`, `h`, `s`, `+`, `-`, `x`, `z`, `b` are all live single-key hotkeys). D-09 specifies a literal `"cal"` command — a 3-character sequence — typed over the same USB serial connection. Naively extending the existing per-character `switch` cannot represent a multi-character command without either colliding with the single-char scheme (e.g., a bare `'c'` keystroke would need to *not* fire anything by itself while the parser waits to see if `'a'` and `'l'` follow) or breaking backward compatibility with the existing hotkeys.
**Why it happens:** The existing bench harness protocol was designed before any multi-character command existed; grafting one on requires a small state machine (accumulate characters, compare against `"cal"`, timeout/reset on a non-matching or delayed sequence) that doesn't currently exist anywhere in this codebase to copy from.
**How to avoid:** Design this explicitly as a small addition — e.g., buffer incoming characters into a short fixed-size ring, and only after a line terminator (`\n`) or a short inter-character timeout, compare the accumulated buffer against `"cal"`; single characters that don't build up to a recognized multi-char command still fall through to the existing single-char `switch` unchanged. Keep this as a named, testable unit (not inlined ad hoc into the existing `if (c == 'r') ... else simHandleCommand(c)` chain) since it is new command-parsing surface, however small.
**Warning signs:** Typing `"cal"` on the bench serial monitor accidentally also triggers the existing `'c'`-adjacent... (no `'c'` hotkey exists today, but any future single-char addition starting with `c`/`a`/`l` would silently break this if the two schemes aren't cleanly separated).

### Pitfall 6: HTU21D and other libraries' internal `delay()` calls are invisible blocking cost that doesn't show up in a quick read of the calling code

**What goes wrong:** `envSensor.poll()` looks like a simple non-blocking call site at the `main.cpp` level, but `Adafruit_HTU21DF::readTemperature()`/`readHumidity()` each internally call `delay(50)` — a total of up to ~100ms per full temp+humidity read, invisible unless the library's source is actually read (as this research did — see Sources).
**Why it happens:** Arduino sensor libraries commonly hide fixed conversion-wait delays inside otherwise innocuous-looking getter methods; nothing in the public API signature (`float readTemperature()`) signals "this blocks for 50ms."
**How to avoid:** Budget HTU21D's ~100ms combined read cost explicitly against the ~266ms GPS UART buffer window (Pitfall 1) when choosing `DEFAULT_HTU21_POLL_MS`, and read the actual source of any new dependency before assuming a getter is "fast" just because its name suggests a register read.
**Warning signs:** None visible from `main.cpp` alone — this is a "looks done but isn't" pitfall that only bench soak-testing (watching `[HEALTH]`'s NMEA-loss counters specifically in the seconds after an HTU21D read) will surface.
