## Fixed Issues

### CR-01: `i2cRecoverTick()` forces modules "online" regardless of the driver's own re-init result

**Files modified:** `firmware/gps_tracker/src/main.cpp`
**Commit:** eb90016
**Applied fix:** Removed the unconditional `i2c_bus::setOnline(m, true)` call that followed each driver's `begin()` in every `case` of `i2cRecoverTick()`'s switch. Each driver's own `begin()` already reports its real result via `i2c_bus::setOnline()` internally (confirmed by reading `accel_sensor.cpp:52`, `mag_sensor.cpp:108/123`, `env_sensor.cpp:33`, `display.cpp:69/80/86`), so the override was actively defeating the online/offline health model. The `"[I2C] %s recovered"` log line is now gated on `i2c_bus::online(m)` actually being true after `begin()` returns, and `i2c_bus::clearReinit(m)` still runs unconditionally (success or not), per the header contract ("Driver calls this after attempting re-init, success or not").

### CR-02: `i2c_bus::present()` never reflects anything beyond the one-time boot scan

**Files modified:** `firmware/gps_tracker/src/i2c_bus.cpp`
**Commit:** 00783db
**Applied fix:** Chose the first of the review's two suggested options (localized, minimal-diff): `retryProbe()` now sets `s_present[addr] = true` immediately after a successful live `probeAddr()`, right alongside its existing `s_boundAddr[idx] = addr` rebind. This means `display::begin()`/`mag_sensor::begin()` (which gate address selection on `i2c_bus::present()`) can now succeed for the OLED or compass even if it was physically absent during the boot-time scan and only connected later — closing the D-13 runtime-recovery gap for those two modules.

### WR-01: Unspecified evaluation order in raw 16-bit accelerometer byte assembly

**Files modified:** `firmware/gps_tracker/src/accel_sensor.cpp`
**Commit:** dc6a089
**Applied fix:** Replaced the three `(int16_t(Wire.read()) << 8) | Wire.read()` expressions with six separate `uint8_t` statements (one `Wire.read()` per statement, per axis high/low byte), then combined the already-read temporaries into `axRaw`/`ayRaw`/`azRaw`. This guarantees a sequence point between each pair of `Wire.read()` calls, eliminating the unspecified-evaluation-order risk the review flagged (and avoiding the noted comma-declaration pitfall, which has the same problem).

### WR-02: Per-driver `reinitDue()` handling in `poll()`/`render()` is dead code

**Files modified:** `firmware/gps_tracker/src/accel_sensor.cpp`, `firmware/gps_tracker/src/mag_sensor.cpp`, `firmware/gps_tracker/src/env_sensor.cpp`, `firmware/gps_tracker/src/display.cpp`
**Commit:** 9e0f2fe
**Applied fix:** Took the review's first suggested option (minimal, consistent with the CR-01 fix that keeps `main.cpp::i2cRecoverTick()` as the sole reinit path): removed the unreachable `if (i2c_bus::reinitDue(...)) { begin(); i2c_bus::clearReinit(...); }` branch from each of `accel_sensor::poll()`, `mag_sensor::poll()`, `env_sensor::poll()`, and `display::render()`. Each now simply returns/exits early while offline, with a comment pointing to `i2cRecoverTick()` as the actual recovery driver. Confirmed via `grep -n "reinitDue"` that no driver `.cpp` file references it anymore outside of comments — only `i2c_bus.cpp` (implementation) and `main.cpp` (the one live call site) do.
